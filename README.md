### Експеримент 1 — Блокуючий цикл 100 мс

**Що змінити** — у `src/main.js`, всередині `render()`:

```js
// Додати на початок render():
if (Math.random() < 1 / 60) {
  const t = performance.now();
  while (performance.now() < t + 100) {}
}
```

**Що побачили:**

| Показник | До | Під час експерименту |
|----------|-----|----------------------|
| frames/s | ~60 | _(запишіть)_ |
| frame time | ~16 ms | _(запишіть, очікується ~100+ ms)_ |
| Візуально | плавно | _(стuttering / фриз)_ |

**Пояснення через event loop:**

JavaScript працює в **одному потоці**. Поки `while`-цикл крутиться 100 мс, **нічого іншого не виконується** — ні rAF, ні обробники кліків, ні малювання. Event loop не може взяти наступну задачу, поки поточна функція не повернеться. Синхронний блок **неможливо** «обійти» з того ж потоку — треба винести роботу в Web Worker або розбити на частини.

### Експеримент 2 — setInterval замість requestAnimationFrame

**Що змінити** — у `src/loop.js` замість rAF:

```js
// Замість rafId = requestAnimationFrame(frame):
rafId = setInterval(() => frame(performance.now()), 16);

// У stop() замість cancelAnimationFrame:
clearInterval(rafId);
```

**Результати (запишіть свої числа):**

| Метрика | rAF | setInterval(16) |
|---------|-----|-----------------|
| frames/s (10 сек) | _(~60)_ | _(запишіть)_ |
| jitter frame time | низький | _(вищий — запишіть)_ |
| У фоновій вкладці 5 сек | пауза | _(продовжує? запишіть)_ |

**Три причини, чому rAF краще:**

1. **Синхронізація з монітором** — rAF викликається перед paint, setInterval — ні.
2. **Економія батареї** — rAF зупиняється у прихованій вкладці, setInterval — ні.
3. **16 ≠ 16.667** — setInterval(16) дає ~62.5 fps, не 60; накопичується drift.

### Експерiment 3 — Змінний крок замість фіксованого

**Що змінити** — у `src/loop.js`, замінити accumulator-цикл:

## Відповіді на Reflection (для захисту)

### 1. Event loop — схема

```
[Call Stack] ← виконується зараз
[Web APIs]   ← setTimeout, DOM, fetch, rAF (браузер)
[Task Queue] ← macrotasks (setTimeout, click)
[Microtask Queue] ← Promise.then, queueMicrotask
```

`setTimeout(f, 0); Promise.resolve().then(g);`  
→ f у task queue, g у microtask queue  
→ stack порожній → **спочатку g**, потім f

### 2. Чому 100 ms синхронний цикл заморожує сторінку?

JS monothread — поки цикл крутиться, event loop заблокований. CSS-анімації можуть продовжуватись (комpositor thread), але JS, scroll handlers, rAF — ні.

### 3. Microtasks vs tasks

- **Правило:** після кожного task — drain **усі** microtasks, потім render (можливо), потім наступний task.
- Microtask chain може **голодувати** rendering — браузер не малює, поки черга microtasks не спустошиться.

### 4. Де rAF відносно tasks/microtasks/paint?

rAF — **rendering step**, після tasks і microtasks, перед style/layout/paint.

### 5. Accumulator loop

- **Clamp dt** — після hitch (Alt+Tab) не симулювати 300 кроків одразу.
- **alpha** — скільки «між» двома симуляційними станами; renderer малює `lerp(prev, curr, alpha)`.

### 6. Детермінізм і мультиплеєр

Однакові inputs + фіксований STEP → однакова позиція на всіх клієнтах. Server може перевірити/передбачити стан.

### 7. Closure — values чи variables?

**Variables (посилання).** `var i` в циклі — всі callback бачать одне `i` (= 3). `let i` — кожна ітерація нова змінна.

### 8. `type="module"` — 5 змін

1. Strict mode автоматично  
2. Свій scope (немає глобальних `var`)  
3. `import`/`export`  
4. Deferred (виконується після parse)  
5. `this` на top-level = `undefined`
